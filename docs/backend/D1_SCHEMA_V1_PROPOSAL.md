# FANEVA SYSTEM V2 — proposed Cloudflare D1 schema v1

## Status and change boundary

**DESIGN PROPOSAL ONLY — NOT AN APPROVED OR APPLIED D1 MIGRATION.**

This is a reviewable relational design for the isolated V2 STAGING backend. It does not create a D1 database, execute SQL, provision Cloudflare resources, deploy a Worker, import the synthetic seed, or change Android/Room schemas. Do not treat these proposed names or columns as an existing live schema.

- Target: a newly created, verified-empty V2 STAGING D1 only.
- V1 is completely excluded. No V1 resources, credentials, identifiers, or data are reused.
- The existing Android Room v7 schema is a separate local database and is not the D1 schema source.
- PR #2 remains Draft until design review, migration implementation, tests, and explicit merge approval.

## 1. Design principles

1. D1 is the authoritative server-side store for shared business state.
2. Tenant isolation is explicit: every business row belongs to one tenant; store-scoped rows also carry a store ID and must be checked against the tenant's store registry.
3. IDs are stable opaque TEXT identifiers generated by trusted application code. Never use display names as keys.
4. All timestamps are UTC ISO-8601 text generated/validated by the server.
5. All monetary values use SQLite INTEGER and whole MGA only, constrained to 0..9007199254740991. No REAL/float money columns.
6. Stock quantities use INTEGER. Signed movement deltas are allowed; balances must never become negative unless a separately approved business rule permits it.
7. Every mutable business aggregate has an integer `version`. Updates require `expectedVersion`; mismatch returns `VERSION_CONFLICT`. No last-write-wins.
8. A mutation receipt, business write, stock/debt effect, change-log event, and audit event commit in one transaction. ACK only after commit.
9. Idempotency keys are unique per tenant and device. Pull cursors are separate, server-owned monotonically increasing integers.
10. Authorization is evaluated server-side on every request. Unlisted operations are denied.

## 3. Proposed key columns and constraints

### Tenant and store registry

- `tenants(id, code, status, created_at_utc)`; unique tenant code.
- `stores(id, tenant_id, code, name, status, created_at_utc)`; unique (tenant_id, code), FK tenant.
- Every tenant-owned table has `tenant_id`; every store-owned row has `store_id` and composite FK (tenant_id, store_id) to stores (requires UNIQUE(tenant_id,id)).
- Store codes A1–A5 are fixture values, not global IDs.

### Accounts, scope, and devices

- `accounts(id, tenant_id, username, role, status, created_at_utc, updated_at_utc, version)`; unique (tenant_id, username); role constrained to ADMIN, GERANT, VENDEUR.
- `account_store_access(tenant_id, account_id, store_id, granted_at_utc, granted_by)`; composite primary key and tenant-safe FKs.
- Both test ADMIN accounts receive the same authorized scope; neither device nor account has primary-device priority.
- `devices(id, tenant_id, account_id, token_hash, status, created_at_utc, last_seen_at_utc, revoked_at_utc)`; unique device ID, unique token hash, never store raw bearer tokens.
- `device_enrollment_challenges(id, tenant_id, target_device_id, proof_hash, expires_at_utc, consumed_at_utc, created_by)`; short-lived, one-use, hashed proof only. Raw activation proof is never persisted.
- Customer creation: ADMIN/GERANT. Debt payment: ADMIN only. VENDEUR is restricted to assigned stores and allowed POS actions; it cannot read purchase prices, margins, profit, debt balances, or credit limits. Unlisted actions are denied.

### Master data

- `products(id, tenant_id, code, name, category, unit, active, version, created_at_utc, updated_at_utc)`; unique (tenant_id, code).
- `customers(id, tenant_id, display_name, contact_ref, status, version, created_at_utc, updated_at_utc)`.
- `suppliers(id, tenant_id, display_name, contact_ref, status, version, created_at_utc, updated_at_utc)`.
- Do not expose customer debt/credit-limit fields through the VENDEUR API projection.

### Inventory

- `stock_balances(tenant_id, store_id, product_id, quantity, version, updated_at_utc)`; PK (tenant_id, store_id, product_id); quantity INTEGER NOT NULL CHECK(quantity >= 0).
- `stock_movements(id, tenant_id, store_id, product_id, movement_type, quantity_delta, source_type, source_id, created_at_utc, created_by)`; immutable, signed INTEGER delta; unique source identity where required to prevent double posting.
- **Approved user decision — Opening Stock Option A:** the immutable `OPENING` stock movement is the canonical source event; `stock_balances` is only the current projection. For each (tenant, store, product), create exactly one opening movement and initialize/update the projection in the same transaction. Reconciliation requires the projection to equal the sum of posted movement deltas. Reject any operation producing a negative balance. Never add a separately counted opening balance.
- Purchases add stock and sales reduce stock in the same transaction as their source document and movement record.

### Purchases and sales

- `purchases(id, tenant_id, store_id, supplier_id, document_number, status, total_mga, version, created_at_utc, created_by)`.
- `purchase_lines(id, tenant_id, purchase_id, product_id, quantity, unit_cost_mga, line_total_mga)`; positive integer quantity; whole MGA unit cost and total.
- `sales(id, tenant_id, store_id, sale_type, customer_id, document_number, status, total_mga, version, created_at_utc, created_by)`; `sale_type` is `CASH` or `CREDIT`; `customer_id` is nullable only for `CASH` and mandatory for `CREDIT`. Enforce with server-side validation (and a compatible database CHECK constraint), including update/import paths; `CREDIT` must reference a valid customer in the same tenant.
- `sale_lines(id, tenant_id, sale_id, product_id, quantity, unit_price_mga, line_total_mga)`; positive integer quantity; whole MGA unit price and total.
- Header totals must equal the sum of persisted line totals. Prices are immutable snapshots for the transaction; edits require explicit versioned correction, not silent overwrites.

### Debt and financial adjustments

- Do not treat a client-supplied balance as authoritative.
- `credit_notes(id, tenant_id, store_id, original_sale_id, credit_note_number, status, total_mga, version, created_at_utc, created_by, reversed_at_utc, reversal_of_id)`; immutable once posted, references exactly one original sale/invoice. One invoice may have multiple credit notes; a credit note cannot span invoices.
- `credit_note_lines(id, tenant_id, credit_note_id, original_sale_line_id, product_id, credited_quantity, original_unit_price_mga, line_total_mga)`; each row maps to one original invoice line. Product and unit price are snapshots from that original line; line total is derived using integer MGA arithmetic. Enforce cumulative credited quantity/value against the original line's remaining eligible quantity/value.
- Credit-note cancellation is an explicit reversal event; never delete or overwrite a posted credit note.
- Do not automatically mutate stock merely because a financial credit note is issued. If goods are physically received, record that receipt as a distinct stock-return event/movement; the exact stock-return workflow and authorization remain subject to separate approval.
- `financial_adjustments(id, tenant_id, store_id, customer_id, adjustment_type, amount_mga, status, version, created_at_utc, created_by)`.
- **Proposed finance semantics (pending approval):** discounts before posting are included in net sale-line amounts and `F_c` is the posted net invoice total. Any reduction after posting requires an immutable invoice-linked Credit Note; never edit a posted invoice. Product-return credit notes use original invoice-line quantity/unit price; physical receipt is a separate stock-return movement. `FinancialAdjustment` is only for source-linked corrections outside invoice/return workflows and cannot silently change invoice balance or stock. Tax configuration/calculation remains disabled until Madagascar tax treatment is verified. `CN_c` means posted Credit Notes for the invoice; `P_c` means posted, non-reversed payment allocations to that invoice.
- `financial_adjustment_sources(id, tenant_id, adjustment_id, source_type, source_id, allocated_amount_mga)`; 1:N provenance from adjustment to source documents.
- `debt_payments(id, tenant_id, store_id, customer_id, amount_mga, status, created_at_utc, created_by, idempotency_key)`; one immutable payment receipt per received payment; ADMIN-only mutation.
- `debt_payment_allocations(id, tenant_id, payment_id, sale_id, amount_mga, status, created_at_utc, created_by, reversal_of_id)`; one row allocates part of one payment to exactly one CREDIT invoice; a payment may have many allocation rows and an invoice may receive allocations from many payments. `P_c` is the sum of posted, non-reversed allocations for that invoice. Sum of allocations per payment must not exceed payment amount; each allocation must not exceed the invoice outstanding collectible balance at posting time. Payment, allocation and invoice must share tenant and customer; reject allocation to CASH invoices. Any unallocated remainder is explicit unapplied customer credit and does not reduce invoice balances. Allocation/reversal operations are append-only, idempotent and server-validated.
- Calculated invoice balance follows the approved rule: `CalculatedInvoiceBalance = F_c - CN_c - P_c`.
- **Approved credit-note cardinality:** each immutable credit note references exactly one original invoice; one invoice may have multiple credit notes. A credit note cannot reference or allocate across multiple invoices. Cancellation is an explicit reversal event; posted history is never deleted or overwritten.
- **Approved credit-note line model — Option A:** each `credit_note_lines` row references the corresponding original `sale_line` and records the product, credited/returned quantity, and the unit price captured on that original invoice line. The line amount is derived from the immutable original unit price and credited quantity using whole-MGA integer arithmetic. Cumulative credited quantity/value must not exceed the original line's remaining eligible quantity/value. Do not automatically mutate stock merely because a financial credit note is issued; physical goods receipt must be a distinct stock-return event. The exact stock-return workflow and authorization remain open.
- Exact credit-note line/amount allocation rules, maximum eligible credit amount, and full source mapping for F_c, CN_c and P_c must be confirmed in the finance domain review before DDL is finalized.
- `supplier_refunds` is a separate register; do not fold supplier refunds into customer debt/payment records.

### Sync, bootstrap, and audit

- `mutation_receipts(id, tenant_id, device_id, idempotency_key, mutation_id, request_hash, outcome, response_json, created_at_utc)`; unique (tenant_id, device_id, idempotency_key) and unique mutation identity as agreed by protocol. Never store credentials in response JSON.
- `tenant_sync_state(tenant_id, last_cursor, version, updated_at_utc)`; one authoritative cursor allocator row per tenant, updated transactionally to serialize concurrent writers.
- `change_log(cursor, tenant_id, event_id, entity_type, entity_id, store_id, event_type, payload_json, created_at_utc)`; cursor is server-owned, strictly increasing per tenant, allocated in the same D1 transaction as the business mutation and change-log insert. Use the tenant sync-state row for serialization; contention triggers safe retry or a retryable conflict. No Android-generated cursor values.
- `device_cursors(tenant_id, device_id, last_cursor, updated_at_utc)`; one row per enrolled device; advance only after a complete, validated pull response. Mutation idempotency receipts are separate from pull cursors.
- `device_cursors(tenant_id, device_id, last_cursor, updated_at_utc)`; one row per enrolled device.
- `bootstrap_imports(tenant_id, environment, seed_id, seed_version, seed_checksum, import_status, record_counts_json, created_at_utc, committed_at_utc)`; unique (tenant_id, environment); one committed seed per fresh tenant.
- `audit_events(id, tenant_id, environment, sequence, actor_id, device_id, event_type, entity_type, entity_id, payload_hash, previous_hash, event_hash, hash_algorithm, hash_version, occurred_at_utc)`; append-only; unique (tenant_id, environment, sequence); server computes SHA-256 chain values. Exactly one server-created `GENESIS` per tenant/environment starts at sequence 1 with a 32-byte zero previous hash. Canonical payload bytes are Unicode NFC-normalized RFC 8785 (JCS) JSON encoded as UTF-8; reject duplicate keys, floats, NaN/Infinity. Hash frame is: ASCII `FANEVA-AUDIT-V1` + NUL; tenant ID NFC UTF-8 prefixed by unsigned 32-bit big-endian byte length; sequence unsigned 64-bit big-endian; previous hash 32 raw bytes; canonical event bytes prefixed by unsigned 64-bit big-endian byte length. `event_hash = SHA-256(frame)`. Store `hash_algorithm=SHA-256`, `hash_version=FANEVA-AUDIT-V1`. Server is authoritative; client hashes are never trusted. A mismatch returns `AUDIT_CHAIN_INVALID`; chain recovery must be an auditable appended event, never a silent reset.

## 4. Index and integrity requirements

At minimum, migration review must include:
- Unique tenant code; unique store code per tenant; unique product code per tenant; unique username per tenant.
- Composite tenant-safe foreign keys for all tenant/store-scoped relations.
- Indexes for store/product stock lookup, customer and supplier search keys, document lookup by store/date, debt/payment by customer/store, movement history by store/product/date, change-log cursor pagination, device status, and audit sequence.
- CHECK constraints for allowed role/status/type values, nonnegative monetary integers within the safe integer bound, positive document-line quantities, nonnegative stock balances, and valid import status.
- Explicit ON DELETE policy. Use RESTRICT for financial, stock, audit, device, mutation-receipt, and synchronization history; do not cascade-delete immutable ledgers or tenant evidence.
- **Approved V2 retention policy (user-approved, including 90-day offline grace):** audit events are append-only for at least 10 years. Financial, invoice, debt, purchase, stock and adjustment records are never hard/cascade deleted and are retained at least 10 years after the relevant fiscal period closes, or longer for legal/audit/dispute holds. Minimal mutation idempotency proofs are retained at least 10 years. Change-log rows remain available to active devices; proposed 90-day offline grace requires stale devices to rebootstrap from a verified tenant snapshot before any log compaction. Device identity/revocation history is retained at least 10 years after revocation or tenant closure; credentials are revoked, not records deleted. Customer PII anonymization is permitted only after balances/disputes/legal holds are cleared and only if immutable financial evidence remains intact, with a separate audit event. Tenant closure freezes writes, exports records and revokes devices; no cascade deletion. Validate applicable Madagascar accounting, tax, privacy and limitation rules before production.
- JSON columns are TEXT and must be validated by Worker code; SQLite JSON validity checks may be used only if supported by the selected D1 SQLite runtime and verified in tests.

## 5. Transaction boundaries

### Accept one push mutation

Within one D1 transaction:
1. Authenticate device and resolve account, tenant, role, and assigned store scope.
2. Check mutation/idempotency receipt. If already committed with identical request hash, return the stored outcome; if key reused with different content, reject.
3. Validate entity/action allowlist, required fields, MGA, store scope, expectedVersion, and business invariants.
4. Write domain rows and line rows.
5. Write stock/debt/payment effects and immutable source ledger rows.
6. Append change-log event and audit hash-chain event.
7. Persist final mutation receipt.
8. Commit; only then return ACK.

Definitive business validation or version errors are REJECTED. Transient/database errors do not ACK and remain retryable. Never use last-write-wins.

### Import one synthetic seed

Use one atomic transaction after pre-validation:
1. Confirm tenant has no committed bootstrap record and no domain rows.
2. Insert tenant/store/master data and synthetic business fixture records in FK order.
3. Insert opening stock and ledger events once under the chosen canonical rule.
4. Verify per-store inventory and financial invariants inside the transaction where possible.
5. Insert bootstrap metadata and audit record.
6. Commit all rows together. Any failure rolls back everything.

## 7. Required decisions before migration implementation

1. **Tenant model — APPROVED:** one initial FANEVA SYSTEM V2 tenant created only by controlled STAGING bootstrap; `tenant_id` remains on all tenant-owned rows with tenant-safe composite foreign keys; no public tenant self-registration or tenant-discovery endpoint in this phase. Server-side enrollment resolves tenant identity; clients cannot choose an arbitrary tenant.
2. Confirm account identity and owner-verification lifecycle, including how two equal ADMIN accounts are created without storing credentials in the seed.
3. Opening Stock representation is resolved: immutable OPENING movement is canonical and stock_balances is a projection. Remaining work is to validate the fixture's exact opening event representation and atomic projection rebuild.
4. Credit-note cardinality is approved: one credit note → exactly one original invoice; multiple credit notes may relate to one invoice. Credit-note line model is approved: link each line to its original sale line, use the original invoice unit price and credited quantity, and enforce remaining eligible quantity/value. Financial credit-note issuance does not automatically increase stock; physical goods receipt is a separate stock movement. Payment allocation Option B is approved and P_c is the sum of posted allocations per invoice. Finance edge-case policy is proposed in the financial adjustment/Credit Note definitions and remains pending user approval.
5. **Sale customer optionality — APPROVED:** add an explicit sale type (`CASH` or `CREDIT`); `customer_id` is nullable only for CASH and mandatory for CREDIT. Enforce the invariant server-side, including updates and imported mutations; reject unknown sale types and CREDIT without a valid same-tenant customer.
6. Confirm cursor sequencing strategy under concurrent ADMIN1/ADMIN2 mutations.
7. **Audit genesis and canonical serialization — APPROVED FANEVA-AUDIT-V1:** server-created unique GENESIS per tenant/environment, sequence 1, zero previous hash; NFC-normalized RFC 8785 JCS UTF-8 event bytes; reject duplicate keys and floating-point/non-finite values; exact length-prefixed binary hash frame and SHA-256 algorithm/version are specified in the `audit_events` definition above. Server-authoritative verification, `AUDIT_CHAIN_INVALID` on mismatch, auditable recovery only, and cross-platform golden-vector tests are mandatory.
8. Confirm data retention/deletion behavior for devices, financial records, audit, and tenant closure.

## 8. Verification gates

Before calling this schema approved:
- Produce ordered executable D1 SQL migration files from the reviewed design.
- Apply migrations only to an ephemeral local D1-compatible test database; do not provision Cloudflare.
- Test fresh migration, FK/unique/CHECK constraints, rollback, idempotent mutation, expectedVersion conflict, concurrent writes, tenant/store isolation, role authorization, MGA boundaries, stock reconciliation, debt/payment calculations, bootstrap idempotency, cursor ordering, and audit hash-chain integrity.
- Build a field-by-field seed mapping and test import + forced mid-transaction rollback + repeat import.
- Obtain explicit design approval before any remote D1 provisioning or deployment.

## Conclusion

This proposal gives the D1 model a concrete review baseline, but it is **not yet migration-ready**. The unresolved decisions in section 7 are deliberate blockers, not assumptions to silently fill. No D1 resource has been created or modified and no seed has been imported.
