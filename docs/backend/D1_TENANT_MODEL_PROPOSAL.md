# D1 Tenant Model — single initial tenant proposal

Date: 2026-11-16  
Branch: `feature/staging-backend-foundation`  
Status: **PROPOSAL — NOT USER-APPROVED.** This is a design clarification only. It does not authorize SQL migrations, Cloudflare provisioning, seed import, Worker deployment, APK changes, or PR merge.

## 1. Recommendation

Use **one initial tenant** for the FANEVA SYSTEM V2 STAGING installation, while retaining explicit `tenant_id` on every tenant-owned row and tenant-safe foreign keys.

This is not the same as removing tenant isolation. It means only one tenant record is created for the initial STAGING dataset; the schema still scopes all business records to that tenant.

## 2. Proposed model

### `tenants`

Proposed fields:
- `id` — opaque stable TEXT primary key generated by trusted setup code.
- `code` — stable unique installation/business code; not a display name.
- `display_name` — human-readable label.
- `status` — constrained lifecycle state such as ACTIVE or SUSPENDED.
- `created_at_utc`, `updated_at_utc` — server-generated UTC timestamps.
- `version` — integer optimistic-concurrency version if tenant settings are mutable.

Constraints:
- UNIQUE(`code`).
- All references use tenant ID, not tenant code or display name.
- Tenant record is created only by a controlled setup/bootstrap operation.
- No public self-service tenant creation endpoint in this phase.

### Tenant ownership on all domain tables

Every business, identity, synchronization, and audit row includes `tenant_id`, except where a truly global immutable lookup table is later justified and reviewed.

For store-scoped records:
- `stores` has UNIQUE(`tenant_id`, `id`) and UNIQUE(`tenant_id`, `code`).
- Child tables use composite foreign keys such as (`tenant_id`, `store_id`) → `stores`(`tenant_id`, `id`).
- Cross-tenant references are rejected by database constraints as well as Worker authorization.
- Query handlers derive tenant ID from authenticated server-side device/account context; clients cannot select an arbitrary tenant ID in request payloads.

## 3. Bootstrap lifecycle

1. Provision a newly created, empty V2 STAGING D1 only after separate approval.
2. Apply reviewed D1 migrations.
3. Verify that there are no tenant or business rows.
4. A controlled bootstrap operation creates exactly one initial tenant record and its A1–A5 stores, as part of the synthetic dataset import transaction.
5. Record a unique bootstrap seed ID, version, checksum, and final commit status.
6. Reject a second bootstrap attempt if a committed bootstrap exists for the STAGING tenant.
7. Device enrollment is bound to that tenant by the server; Android devices do not create tenant records.

The seed fixture must not contain passwords, bearer tokens, API keys, enrollment proofs, or pre-authorized device credentials.

## 4. Security invariants

- Tenant ID is resolved from the authenticated device's server-side enrollment record.
- Every API operation checks tenant membership and, where applicable, assigned store scope.
- A client-supplied tenant ID is never an authorization source.
- ADMIN #1 and ADMIN #2 remain equal in authority within the same tenant; neither is a primary device.
- VENDEUR remains restricted to assigned stores and allowed POS operations.
- Unlisted operations are denied.
- No public tenant discovery/listing endpoint is required for this single-tenant deployment.

## 5. Why not implement full multi-tenant onboarding now?

A full multi-tenant product would require additional policy and security work: tenant provisioning, tenant-owner lifecycle, billing or quotas if applicable, tenant discovery, support access, isolation tests, tenant suspension/closure, and cross-tenant administrative controls. None of that is required to validate the current V2 two-device, A1–A5 STAGING workflow.

Keeping `tenant_id` now preserves structural isolation and a possible future expansion path without introducing those unapproved endpoints or operational flows.

## 6. Alternatives

| Option | Advantages | Risks / cost |
|---|---|---|
| One initial tenant, tenant_id everywhere (**recommended**) | Simple controlled bootstrap; preserves relational isolation; supports two ADMIN devices and five stores | Future tenant onboarding requires a separately reviewed lifecycle |
| Full multi-tenant onboarding now | Supports multiple businesses from day one | Larger attack surface, more lifecycle policy, more isolation tests and operational complexity |
| No tenant_id (single-business tables only) | Slightly simpler DDL | Weakens explicit tenant isolation and makes later expansion/migration harder |
